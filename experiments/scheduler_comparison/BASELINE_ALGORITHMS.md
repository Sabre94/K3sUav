# Baseline 算法设计说明

## 算法概述

本实验设计了两个 Baseline 调度算法，用于与后续的优化算法进行对比。

---

## 1. K8s-Default 算法

### 设计思路

模拟 Kubernetes 默认调度器的 **LeastAllocated** 策略：
- 优先选择资源利用率最低的节点
- 平衡 CPU 和内存使用
- 追求资源均衡分配

### 实现细节

```go
type LeastLoadedAlgorithm struct {
    CPUWeight    float64  // CPU 权重 (0.5)
    MemoryWeight float64  // 内存权重 (0.5)
}
```

**评分公式**:
```
cpuAvailable = 100 - cpuUsage
memoryAvailable = 100 - memoryUsage
score = 0.5 × cpuAvailable + 0.5 × memoryAvailable
```

**评分范围**: 0-100（越高越好）

### 算法特点

✅ **优点**:
- 实现简单，计算高效
- 资源利用均衡
- 符合 Kubernetes 调度理念

❌ **缺点**:
- 不考虑节点地理位置
- 不考虑网络延迟
- 不考虑电量消耗
- 可能选择远离中心的节点

### 测试结果（10个节点）

```
选中节点: uav-node-43, 24, 41, 44, 03, 18, 42, 14, 01, 32
平均电量: 46.6%
平均延迟: 50.63 ms
平均CPU:  14.0%  ✓ 资源利用率低
平均内存: 31.4%  ✓ 资源利用率低
距离范围: 0 - 752km（分布极广）
```

**观察**:
- 资源利用率非常低（符合预期）
- 但选择的节点分布极广（距中心0-752km）
- 电量较低（46.6%）
- 延迟中等（50.63ms）

---

## 2. Latency-First 算法

### 设计思路

基于网络延迟的调度策略：
- 优先选择网络延迟最低的节点
- 适合延迟敏感型任务
- 追求最快响应速度

### 实现细节

```go
type NetworkLatencyAlgorithm struct {
    MaxLatency float64  // 最大可接受延迟 (200ms)
}
```

**评分公式**:
```
score = 100 × (1 - latency / maxLatency)
```

**过滤规则**:
- 延迟 > 200ms 的节点直接过滤
- 只对低延迟节点评分

**评分范围**: 0-100（越高越好）

### 算法特点

✅ **优点**:
- 网络延迟最低
- 响应速度快
- 适合实时任务

❌ **缺点**:
- 不考虑资源利用率
- 不考虑电量
- 可能导致资源不均衡
- 倾向选择靠近中心的节点（因为延迟与距离相关）

### 测试结果（10个节点）

```
选中节点: uav-node-01, 04, 03, 07, 19, 05, 10, 17, 18, 13
平均电量: 57.1%  ✓ 电量较高
平均延迟: 23.54 ms ✓ 延迟极低
平均CPU:  26.9%
平均内存: 49.0%
距离范围: 0 - 188km（集中在内圈）
```

**观察**:
- 延迟极低（23.54ms，比 K8s-Default 低 53%）
- 节点集中在内圈（0-188km，比 K8s-Default 小 75%）
- 电量较高（57.1%）
- CPU/内存使用较高（资源不够均衡）

## 算法对比分析

### 指标对比表

| 指标 | K8s-Default | Latency-First | 差异 |
|-----|-------------|---------------|------|
| **平均延迟** | 50.63 ms | **23.54 ms** ✓ | -53% |
| **平均电量** | 46.6% | **57.1%** ✓ | +23% |
| **平均CPU** | **14.0%** ✓ | 26.9% | +92% |
| **平均内存** | **31.4%** ✓ | 49.0% | +56% |
| **节点分布** | 0-752km | **0-188km** ✓ | 集中 |

### 权衡分析

#### K8s-Default
```
优势: 资源均衡（CPU 14%, 内存 31.4%）
劣势: 延迟高（50.63ms）、分布分散、电量低
适用: 批处理任务、资源敏感型任务
```

#### Latency-First
```
优势: 延迟低（23.54ms）、节点集中、电量高
劣势: 资源不均衡（CPU 26.9%, 内存 49%）
适用: 实时任务、延迟敏感型任务
```

---

## 延迟与距离关系验证

根据数据生成规律：`latency = 10 + 0.08 × distance + noise`

### K8s-Default 的问题

选中的节点分布范围 **0-752km**，导致：
- 远距离节点延迟高（60-90ms）
- 平均延迟被拉高到 50.63ms
- **没有考虑地理因素**

### Latency-First 的优势

选中的节点集中在 **0-188km**（内圈），导致：
- 近距离节点延迟低（5-40ms）
- 平均延迟仅 23.54ms
- **自动优选靠近中心的节点**

## 结论

两个 Baseline 算法各有优劣：

1. **K8s-Default** 追求资源均衡，但忽略了地理和网络因素
2. **Latency-First** 追求低延迟，但可能导致资源不均

后续的优化算法需要在以下方面超越 Baseline：
- ✅ 更低的延迟（< 23.54ms）
- ✅ 更均衡的资源利用
- ✅ 更合理的节点分布
- ✅ 更高的电量效率
